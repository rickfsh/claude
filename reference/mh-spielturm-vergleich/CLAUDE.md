# CLAUDE.md — MH Spielturm Vergleich

> Kontext-Datei für KI-Assistenten und Entwickler. Beschreibt Architektur, Datenmodell,
> Konventionen und Stolperfallen des Plugins. **Bei jeder Änderung das Changelog am Ende
> aktualisieren und die Version bumpen (siehe „Arbeitsregeln").**

---

## 1. Was das Plugin macht

Interaktiver **Spielturm-Konfigurator** für WooCommerce-Produktseiten (Mega-Holz). Ersetzt
auf der Produktseite die Standard-WC-Galerie + Summary durch eine 2-Spalten-UI:

- **Links:** Bildergalerie mit Thumbnails, Lightbox (Zoom), optional 360°-Viewer.
- **Rechts:** Design-Auswahl (Serie) → Ausstattung konfigurieren (Toggles) → Preis +
  CTA/Warenkorb. Darunter Tabs (Beschreibung, Zusätzliche Infos, Produktdaten, Bewertungen)
  und eine Vergleichstabelle.

Der Clou: Mehrere Produkte (eine *Gruppe*) werden als **Varianten einer Konfiguration**
dargestellt. Wechselt der Nutzer Serie/Ausstattung, springt die UI auf das passende
WooCommerce-Produkt (eigene ID, eigener Preis, eigener Warenkorb-Eintrag) — ohne Reload.

**Abhängigkeit:** WooCommerce (≥ 7.0). Ohne WC zeigt das Plugin nur eine Admin-Notice.

## 2. Dateistruktur

```
mh-spielturm-vergleich/
├── mh-spielturm-vergleich.php      # Bootstrap, Konstanten, Activation, Migrationen
├── includes/
│   ├── class-data-provider.php     # WC-Daten → Konfigurator-Datenstruktur (+ Cache)
│   ├── class-frontend.php          # Shortcodes, Asset-Enqueue, AJAX, Schema, Skeleton
│   ├── class-360-metabox.php       # WC-Produkt-Tab „360° Ansicht" + statische Helfer
│   └── class-analytics.php         # Event-Tracking (eigene Tabelle) + Admin-Dashboard
├── admin/
│   ├── class-settings.php          # Settings-Seite: Gruppen/Serien/Stufen/Matrix/IDs
│   ├── admin.js                    # Add/Remove-Zeilen für Serien & Stufen
│   └── admin.css
└── public/
    ├── css/  spielturm-vergleich.css · spielturm-lightbox.css · spielturm-360.css (+ .min)
    └── js/   spielturm-vergleich.js · spielturm-360.js (+ .min)
```

> **Hinweis:** Die Spielturm-`.min`-Dateien enthalten echten minifizierten Code (ohne
> Zeilenumbrüche — `wc -l` meldet daher 0 Zeilen, sie sind aber NICHT leer). Der
> Asset-Resolver nutzt sie, wenn vorhanden & nicht-leer, sonst die unminifizierte Variante.
> Für den **Spielhaus**-Konfigurator (ab v5.10.0) gibt es noch keine `.min`-Files →
> dessen Assets werden unminifiziert ausgeliefert (Fallback greift via `filesize > 0`).

## 4. Datenmodell (Option `mh_stv_groups`)

Das Herzstück. Ein Array von **Gruppen**, jede Gruppe:

```php
[
  'group_name'      => 'Spielturm Nino / Pirato',
  'base_features'   => 'Sandkasten, Teleskop, ...',   // immer inklusive, alle Serien/Stufen
  'series'          => [                                // Design-Auswahl (Spalte 1 der UI)
      [ 'key' => 'klassisch', 'label' => '...', 'icon' => '🏠', 'features' => 'Piratenflagge' ],
      // 'features' = Immer-dabei-Extras NUR für diese Serie
  ],
  'levels'          => [                                // Ausstattungsstufen (Toggles)
      [ 'key' => 'basic', 'label' => 'Ohne Schaukel', 'toggle_desc' => '...' ],
      // 'extras' existiert noch (Legacy, leer), wird NICHT mehr als Quelle genutzt
  ],
  'features_matrix' => [                                // ← seit v5.7.0 die Wahrheit
      'klassisch' => [ 'basic' => 'Kletterseil', 'swing' => 'Schaukel, ...', ... ],
      'piraten'   => [ ... ],
  ],
  'products'        => [                                // Serie × Stufe → WC-Produkt-ID
      'klassisch' => [ 'basic' => 1234, 'swing' => 1235, 'full' => 1236 ],
      'piraten'   => [ ... ],
  ],
]
```

**Feature-Logik (wichtig):** Was als „inklusive" / ✓ angezeigt wird, setzt sich zusammen aus
`base_features` (global) + `series[].features` (pro Serie) + `features_matrix[serie][level]`
(pro Kombination). Die `features_matrix` hat v5.7.0 die alten globalen `levels[].extras` ersetzt.

### Option `mh_stv_settings`
`accent_color` (#e8910c), `hide_selector` (alte WC-Galerie ausblenden), `show_stock`,
`payment_selector`, `manufacturer_selector` (Oxygen-Element → Produktdaten-Tab),
`embed_selectors` (Elemente in rechte Spalte, 1/Zeile), `below_grid_selectors`
(volle Breite unter Konfigurator), `trust_1/2/3` (Trust-Signals).

### 360°-Daten
Pro Produkt im Post-Meta `_mh_stv_360_frames` (Array von Attachment-IDs, Reihenfolge =
Drehrichtung). Verwaltet im WC-Produkt-Tab „360° Ansicht".

## 5. Data Provider (`MH_STV_Data_Provider`)

Liest WC-Produkte und baut die JSON-Struktur für `wp_localize_script`.

- **`get_group_for_product($id)`** — findet Gruppe + aktuelle Serie/Stufe für eine Produkt-ID.
- **`build_comparison_data()`** — baut die **leichtgewichtige Basis-Daten** (seit v5.8.0):
  Name, Preis, Galerie-URLs (+ srcset), Thumbs, 360°-Frames, Lagerstatus, Kurzbeschreibung,
  Rating-Count/-Schnitt. **Schwere Felder** (`description`, `attributes`, `product_meta`,
  `reviews`, `gallery_full`) sind `null` → werden per AJAX nachgeladen.
- **`get_product_detail($id)`** — lädt genau diese schweren Felder lazy (AJAX-Endpoint).
- **Caching (#8):** Basis-Daten liegen 1 h in einem Transient `mh_stv_base_<md5(group)>`.
  `is_current` wird beim Cache-Hit pro Seite neu gestempelt. Invalidierung über
  `woocommerce_update_product`, `woocommerce_new_product`, `save_post_product` und beim
  Speichern der Optionen (`invalidate_cache()` löscht alle `mh_stv_base_*`-Transients).

**HPOS-Kompatibilität (v5.7.1):** Meta wird über `$wc->get_meta()` / `get_meta_data()`
gelesen, nicht über `get_post_meta`. GPSR-Herstellerdaten (`_wc_gpsr_*`) werden gemappt
und in den Produktdaten-Tab einsortiert (`section => 'manufacturer'`).

## 6. Frontend (`MH_STV_Frontend`)

**Shortcodes:**
- `[mh_spielturm_vergleich]` — erkennt Produkt automatisch (global `$product`/`$post`/queried).
- `[mh_spielturm_vergleich id="123"]` — explizite ID.
- `[mh_360_viewer id="123" autoplay="true"]` — Standalone-360°, überall platzierbar.

**Asset-Handling:**
- `resolve_asset()` wählt `.min`-Variante falls vorhanden & nicht `SCRIPT_DEBUG`.
- **Versionierung (#4):** Content-Hash (erste 8 Zeichen `md5_file`) statt Plugin-Version →
  „immutable caching", Cache-Bust nur bei echter Dateiänderung.
- JS-Abhängigkeit: `mh-stv-front` hängt an `mh-stv-360` (360°-Modul lädt zuerst).

**AJAX-Endpoints** (alle mit Nonce, je `_priv` + `_nopriv`):

| Action | Zweck |
|---|---|
| `mh_stv_add_to_cart` | Warenkorb; Rate-Limit (12/min/Session), Qty-Max aus Stock, liefert `cart_item_key` für Undo |
| `mh_stv_undo_cart` | Entfernt Cart-Item per Key (v5.4.0) |
| `mh_stv_refresh_bt` | Rendert `[mh_bought_together]` für die aktuell gewählte Produkt-ID neu |
| `mh_stv_product_detail` | Lazy-Load der schweren Detail-Felder (#2) |
| `mh_stv_track` | Analytics (in `MH_STV_Analytics`, nicht hier) |

**Weitere Aufgaben:** baut JSON-LD `Product`-Schema (geht sonst verloren, weil die WC-Galerie
versteckt wird), liefert ein Skeleton-Placeholder (CSS-Pulse) bis JS rendert, und integriert
das `mh-bought-together`-Plugin (rendert es versteckt vor, JS verschiebt es in die rechte Spalte;
Dedup-Flag `$mh_bt_widget_rendered` verhindert doppelte Auto-Platzierung).

## 7. 360°-Viewer

- **`class-360-metabox.php`:** WC-Produkt-Daten-Tab „360° Ansicht". Frames per Media-Library
  hochladen, Drag&Drop-Sortierung (jQuery UI Sortable), Speicherung in `_mh_stv_360_frames`.
  Enthält FFmpeg-Tipp zur Frame-Extraktion (36–72 WebP empfohlen). Statische Helfer
  `get_frame_urls()` / `get_frame_thumb_url()` werden vom Data Provider & Frontend genutzt.
- **`public/js/spielturm-360.js`:** Eigenständiges `MH360`-Modul (ES5, keine Deps).
  `MH360.create(container, {frames, accentColor, autoplay})`. Spinner mit rAF-gedrosseltem
  Drag, Sub-Pixel-Akkumulator, Velocity-Smoothing (EMA), Momentum (Friction 0.85), Autoplay
  (5 fps, Smoothstep-Ramp). Single-Image-Rendering gegen Flicker (seit v1.2.0).

## 8. Analytics (`MH_STV_Analytics`, seit v5.9.0)

Privacy-freundlich, **keine Cookies, keine Personendaten** — nur aggregierte Tageszähler.

- **Tabelle:** `{prefix}mh_stv_analytics` (UNIQUE auf `event_date + event_name + event_value`,
  Inkrement via `INSERT ... ON DUPLICATE KEY UPDATE`). DB-Version in Option `mh_stv_analytics_db`.
- **Tracking:** Frontend sammelt Events, schickt sie gebatcht (max 20/Request) per AJAX
  `mh_stv_track`, beim Unload via `navigator.sendBeacon`. **Allowlist** der Event-Namen:
  `stv_view`, `stv_serie_switch`, `stv_level_switch`, `stv_add_to_cart`, `stv_tab_open`,
  `stv_lightbox_open`, `stv_360_interact`, `stv_bt_interact`, `stv_gallery_swipe`.
- **Dashboard:** WooCommerce → *Produkte* → „Spielturm Analytics". KPI-Karten (Aufrufe,
  Add-to-Cart, **Conversion Rate**, **Engagement Rate**), Chart.js-Verlauf (CDN 4.4.1),
  Top-Tabs & Design-Wechsel, Zeitraum 7/30/90 Tage, **CSV-Export** (`;`-getrennt, UTF-8-BOM
  für Excel, Nonce-geschützt).

## 10. Frontend-JS Architektur (`spielturm-vergleich.js`, ES5)

Liest `mhStvData` (von `wp_localize_script`), rendert in `#mh-stv-configurator`.

- **`state`** = `{ serie, swing, wall, galleryIdx, is360, activeTab, qty }`. Ausstattung wird
  als zwei Booleans (`swing`, `wall`) gehalten und über `levelKey()` auf `basic/swing/full`
  gemappt; `wall` setzt `swing` voraus.
- **Render-Pipeline:** `render()` (baut DOM, Desktop default), `update(resetGallery)` als
  zentraler Refresh; Teil-Updates: `updateDesigns`, `updateToggles`, `updateRight`,
  `buildCTA`, `updateTabs`, `updateGallery`, `buildComparisonView`/`updateComparisonView`.
- **Sticky-Bar:** `initStickyObserver` (IntersectionObserver), `updateStickyTop/CTA/Price/BtPill`,
  Breakpoint 1024px.
- **Lightbox:** `buildLightbox`, `openLightbox`, `toggleZoom`, Thumbstrip, 360°-Slide an Index 1.
- **Performance:** `imageCache` mit `preloadImage` (kein DOM-Stacking, seit v5.2.0),
  `preloadAdjacentImages` / `preloadProductGallery`.
- **Sicherheit:** `sanitizeHTML()` strippt Scripts + Event-Attribute aus nachgeladenem HTML.
- **`prefers-reduced-motion`** wird respektiert (Preis-Animation etc.).

## 12. Spielhaus-Konfigurator (ab v5.10.0)

Zweiter, eigenständiger Konfigurator-Typ — bewusst getrennt vom Spielturm gehalten, damit
dessen Code regressionssicher bleibt. Konzeptioneller Unterschied: der Spielturm mündet in
**ein** Produkt, das Spielhaus ist ein **Bundle** (Basis-Haus + separate Zubehör-Positionen).

**Status:** Schritt 1–6 + Redesign (v5.13.0) fertig. Schritt 1–3 (Admin/Datenmodell,
Data-Provider, Frontend-Render + Live-Summe mit Rabatt-Vorschau). **Schritt 4 (v5.11.0):**
Bundle-Add-to-Cart — Haus + alle gewählten Extras in EINEM AJAX-Call, jede Position mit
`_mh_sh_*`-Cart-Meta getaggt (Muster aus `mh-bought-together` portiert). **Schritt 5 (v5.11.0):**
Rabatt-Engine als **Positionspreis** via `woocommerce_before_calculate_totals` (NICHT als Fee),
idempotent, reagiert aufs Entfernen von Haus/Extras. **Schritt 6 (v5.12.0):** Analytics-Tracking
+ Galerie-Lightbox + geteilter 360°-Spinner (Details unten). **Redesign (v5.13.0):** komplette
Frontend-Überarbeitung (Details unten unter „Redesign v5.13.0").

**Redesign v5.13.0:** (1) **Modell-Karten** statt Pills — pro Haus Tag/Badge, Größe (mit
Lineal-Icon), Größen-Balken (`size_pct`) und Kurzbeschreibung (`blurb`), plus UVP-Streichpreis
und „ab"-Preis. Diese vier Felder sind **im Admin frei pflegbar** (siehe unten). (2) **Galerie**
neu: großes Hauptbild + alle weiteren Bilder ebenfalls **groß** im 2-Spalten-Raster darunter
(kein Thumbnail-Streifen mehr); **jedes** Bild öffnet die Lightbox (`LB.open(imgs, idx, [])` —
leere Frames = **kein 360° mehr im UI**, `spin_frames` bleibt im Payload, nur ungenutzt).
(3) **Zubehör-Karten** gestapelt (`.mh-sh-extras-list`): ganze Zeile klickbar zum An-/Abwählen,
Stepper erst sinnvoll bei `allow_qty`, **Details-Akkordeon** aus `short_description` (nur wenn
vorhanden), UVP-Streichpreis + Set-Streichpreis (grüner Bundle-Netto) + Badges (`−X%`, `−Y% im
Set`, OOS). (4) **Lagerstatus ein-/ausblendbar** über globale Option `mh_stv_sh_show_stock`
(Default an); **nicht lieferbare Artikel bleiben in beiden Fällen wählbar** (kein `disabled`).
(5) **Zusammenfassung** mit durchgestrichener Gesamt-UVP + „Du sparst"-Pill (UVP- *und*
Set-Rabatt kombiniert); **mobile Sticky-CTA-Leiste** (`.mh-sh-mobilebar`, ab ≤980px, Desktop-CTA
dann versteckt). Set-Rabatt bleibt **plugin-gesteuert** über `discount_tiers`/`tier_percent`.
**Neue Payload-Felder** in `build_product_base`: `regular_price` (display) + `on_sale` — Basis
für alle Streichpreise (Haus + Add-ons). **Neue Haus-Felder** im Datenmodell + Payload:
`tag`, `size`, `size_pct` (0–100), `blurb`.

**Schritt 6 — Analytics:** Eigener `stv_sh_`-Event-Namespace, geht durch dieselbe Pipeline wie
der Spielturm (`mh_stv_track`, gebatcht via `fetch`, `pagehide`→`sendBeacon`-Flush). Im JS
gespiegelter `track()`-Helfer; localize liefert zusätzlich `trackNonce` (Nonce `mh_stv_track`).
Events: `stv_sh_view` (Init, Wert = Haus-ID), `stv_sh_house_switch` (Wert = Haus-ID),
`stv_sh_extra_toggle` (Wert = `addonId:on|off`), `stv_sh_add_to_cart` (Wert = `hausId:extraCount`),
`stv_sh_lightbox_open` (Wert = `photo|360`), `stv_sh_360_interact` (Wert = `inline|lightbox`),
`stv_sh_share` (v5.42.0, Wert = `desktop|mobile` — welcher Teilen-Button).
Alle sind in `class-analytics.php` **sowohl** in der Allowlist (`ajax_track`) **als auch**
in `$labels` (Dashboard-Tabelle) eingetragen — beide Listen müssen synchron bleiben.

**Schritt 6 — 360° + Lightbox:** Wiederverwendung des geteilten `MH360`-Moduls (kein Code-Dup):
`class-spielhaus-frontend.php` registriert `mh-stv-360` (JS+CSS) defensiv mit gleichem Handle
(`wp_script_is`/`wp_style_is`-Guard → keine Doppel-Ladung), `mh-sh-front` (JS+CSS) hängt als
Dependency daran. Die Lightbox selbst ist **eigenständig** im Spielhaus-JS gebaut (eigene
`mh-sh-lb-*`-Klassen, an `<body>` gehängt) — NICHT die Spielturm-Lightbox portiert, da diese eng
an den Spielturm-State gekoppelt ist (Regressionsschutz). Features: Hero klickbar (Zoom-Hint),
Thumbstrip, Prev/Next, Zähler, Tastatur (Esc/←/→), Touch (horizontal blättern, runter wischen =
schließen), Scroll-Lock, Bild-Vorladung der Nachbarn. 360°: Inline-Spinner im Hero (nur wenn
`spin_frames` vorhanden) mit Exit-Button; dessen `onExpand` öffnet die Lightbox im 360°-Modus
(`MH360.create` im Lightbox-Stage, Nav/Foto ausgeblendet). Quelle der Frames: `spin_frames` aus
`MH_STV_360_Metabox` (geteilt mit dem Spielturm). Lightbox-Bilder: `gallery_full` falls geladen,
sonst `gallery` (Indizes stimmen überein, da gleiche Galerie-Reihenfolge).

**Cart-Item-Meta (Schritt 4) — Namespace `_mh_sh_*`:**

| Key | Bedeutung |
|---|---|
| `_mh_sh_bundle_id` | Eindeutige ID (`mhsh_<haus>_<time>_<rand4>`), gruppiert die Positionen eines Sets |
| `_mh_sh_role` | `house` \| `extra` (inkludierte Add-ons werden NICHT in den Cart gelegt) |
| `_mh_sh_source_house` | `base_product_id` des Hauses (Re-Auflösung der Staffeln) |
| `_mh_sh_group` | Gruppen-Index (Re-Auflösung; zusammen mit `source_house` + product_id eindeutig) |
| `_mh_sh_applied_pct` | Runtime-Stash des angewendeten %-Satzes (Anzeige + Bestellmeta) |

**Wichtig — Source of Truth:** Der Add-to-Cart-Handler und die Rabatt-Engine vertrauen NIE den
Frontend-Werten. Haus, gültige (nicht-inkludierte) Add-ons, `allow_qty`/`default_qty` und die
`discount_tiers` werden server-seitig über `MH_STV_Spielhaus_Data_Provider::get_house_def()` /
`get_addon_tiers()` / `tier_percent()` aus der Option re-aufgelöst und validiert (Lager, Kaufbarkeit).

**Rabatt-Engine (`apply_bundle_pricing`, Hook-Prio 20):**
1. Cart nach `_mh_sh_bundle_id` gruppieren → pro Bundle: Haus vorhanden? + Extra-Keys sammeln.
2. `D = count(extra_keys)` (verschiedene Extras im Cart; Stückmenge egal).
3. Pro Extra: Staffel-% aus der Option (`tier_percent(get_addon_tiers(...), D)`); `set_price(base × (1 − %/100))`.
4. **Idempotenz:** Basispreis je Cart-Item-Key einmal pro Request festgehalten (`base_price()`,
   statisch) → kein Aufschaukeln bei Mehrfach-Feuern. **Reaktion aufs Entfernen:** D wird jeden Lauf
   frisch gezählt; fehlt das Haus, entfällt der Rabatt (Extras zurück auf vollen Preis).
5. Haus & inkludierte Positionen werden nie angefasst.

**Cart-/Bestell-Integration:** `woocommerce_get_cart_item_from_session` stellt die `_mh_sh_*`-Meta
nach Reload wieder her (sonst Verlust); `woocommerce_get_item_data` zeigt „Set-Rabatt −X %" je
Zeile; `woocommerce_checkout_create_order_line_item` schreibt die Bundle-Meta + den (autoritativ
neu berechneten) Rabattsatz an die Bestellpositionen.

**AJAX-Actions (neu):** `mh_stv_sh_add_to_cart` (`_priv`+`_nopriv`, Nonce `mh_stv_sh_add_to_cart`,
Rate-Limit 12/min/Session). Liefert `cart_count`, `cart_url`, Mini-Cart-`fragments`, `notices`
(z. B. Lager-Anpassungen) und die `cart_keys`.

**Entscheidung (dokumentiert):** Inkludierte Add-ons (`included:true`) werden bewusst **nicht** als
eigene Warenkorb-Positionen angelegt — sie gehören zum Lieferumfang des Hauses (Preis 0, nicht in
der Summe). Einziger Eingriffspunkt, falls 0-€-Positionen fürs Picking gewünscht sind: der
Extras-Loop in `MH_STV_SH_Frontend::ajax_add_to_cart()`.

**Dateien:** `admin/class-spielhaus-settings.php` (+ `spielhaus-admin.js` / `.css`),
`includes/class-spielhaus-data-provider.php`, `includes/class-spielhaus-frontend.php`,
`public/js/spielhaus-konfigurator.js`, `public/css/spielhaus-konfigurator.css`.

**Option `mh_stv_spielhaeuser`** (Datenmodell): Array von Gruppen. Eine Gruppe = ein
Konfigurator (Auswahl zwischen N Häusern, wie `series` beim Spielturm).

```
group: { group_name, houses: [ {
  base_product_id,            // Spielhaus = WC-Produkt, NIE rabattiert
  label, layout,              // layout: standard | wide | compact (Frontend-Renderer)
  tag, size, size_pct, blurb, // Modell-Details (v5.13.0), frei im Admin pflegbar →
                              //   tag=Badge, size=Maßtext, size_pct=Balken 0–100, blurb=1 Satz
  addons: [ {
    product_id,
    included,                 // true = "im Lieferumfang", kein Toggle, nie rabattiert, nicht in der Summe
    default_qty, allow_qty,   // Mengen-Vorauswahl + im Frontend änderbar
    discount_tiers: [ { from_distinct, percent } ]   // nur Extras; aufsteigend sortiert
  } ]
} ] }
```

**Zweite Option `mh_stv_sh_show_stock`** (v5.13.0, bool, Default 1): globaler Schalter
„Lagerstatus im Konfigurator anzeigen". Im selben Settings-Group `mh_stv_spielhaus_options`
registriert (Checkbox mit Hidden-0-Muster), per Localize als `mhShData.showStock` ins Frontend.
Unabhängig davon bleiben nicht lieferbare Artikel **immer wählbar**.

**Payload-Preisfelder (v5.13.0):** `build_product_base()` liefert zusätzlich `regular_price`
